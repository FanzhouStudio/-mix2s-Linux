Revision 4 itself has not been booted: those modules were transferred into the already-running revision 3 RAM environment over ACM and loaded there. The kernel registered a Synaptics S3330 RMI4 device with firmware ID `2812197` and created an input event device. This establishes driver registration; physical touch coordinates were not checked.

The live Bluetooth probe loaded the matching `ecc`, `ecdh_generic`, `rfkill`, `bluetooth`, `btqca`, `btbcm`, and `hci_uart` modules and used Polaris firmware `crbtfw21.tlv` and `crnv21.bin`. The kernel reported WCN3990 setup completed. This confirms controller firmware initialization, but Bluetooth scanning and pairing were not tested.

Revision 5 is built from the same Kali `6.1-sdm845` kernel machine code and peripheral-mode DTB. Its DTB adds `qcom,snoc-host-cap-skip-quirk` to `wifi@18800000`, the Polaris workaround documented in [Kali bug 9767](https://bugs.kali.org/view.php?id=9767). The initramfs includes matching ath10k SNOC, mac80211, cfg80211, QCA Bluetooth, touch, and WCNSS support modules plus the Kali WCN3990 and Bluetooth firmware assets. It locates the modem, vendor, and DSP GPT partitions by `PARTNAME`, mounts VFAT read-only and ext4 with `ro,noload`, then creates firmware-name aliases in RAM. It starts USB ACM before the radio probes so a delayed firmware request should not block the diagnostic shell.

Revision 5 was booted. Its active device tree contains `qcom,snoc-host-cap-skip-quirk`, but `qrtr-lookup 69` showed no WLFW service and `wlan0` did not appear. The modem remoteproc had repeated crash/recovery events. The v5 initramfs also did not start the Qualcomm userspace services on its own; these services are required for SDM845 Wi-Fi. During the live probe, `tqftpserv` was placed at `/tmp/tqftpserv`, the same path it uses as a temporary directory, and its log reported “Not a directory.” The v5 WLAN firmware alias also pointed to a generic `wlanmdsp.mbn`; the device's OEM blob in the read-only modem partition has a different hash.

## Revision 6 and 7 live tests; revision 8

Revision 6 booted on-device and reached its diagnostic shell. Live reads showed that `/sys/class/remoteproc/remoteproc0` is the modem (`firmware` is `qcom/sdm845/polaris/mba.mbn`), while `remoteproc2` is the CDSP. The v6 script incorrectly started remoteproc2, leaving the modem offline. It also copied PD map JSON files into `/lib/firmware/updates/...`, while pd-mapper discovers maps beside the firmware paths exposed by remoteproc. Its log therefore said `no pd maps available`.

In the running v6 RAM environment, starting the modem at `remoteproc0`, copying `modemuw.jsn`, `adspr.jsn`, and `cdspr.jsn` beside the Polaris remoteproc firmware, and restarting pd-mapper made WLFW service 69 appear. Then `/sys/class/net/wlan0` appeared. ath10k logged WCN3990 target and firmware details and chose a random MAC because the reported address was invalid. `ip link set wlan0 up` succeeded; the interface reports `UP` with no carrier. The initramfs does not include `iw` or a supplicant, so radio scanning and association are not established.

Revision 7 locates the modem remoteproc by its `mba.mbn` firmware path and stages PD map JSON beside the remoteproc firmware. It booted on-device; the modem reached `running`, touch registered as Synaptics S3330, and Bluetooth registered `hci0` and completed QCA firmware setup. pd-mapper exited at first start because the remoteproc firmware nodes had not yet been registered. Restarting pd-mapper after module loading made WLFW service 69 appear and created `wlan0`. ath10k reported the WCN3990 firmware loaded; `wlan0` could be set UP but had no carrier. Build with `python3 diagnostics/build-kali61-v2.py --revision 7`. Artifact SHA-256: `92d1963bba5d6367df6c10786db8e09a91aa745dfa720818f551a4eb03a1d0b8`.

Revision 8 keeps RMTFS and TFTP ready, then loads QCOM remoteproc modules so pd-mapper can discover firmware paths, starts pd-mapper, and only then starts the modem. This addresses the v7 first-start ordering failure. Build with `python3 diagnostics/build-kali61-v2.py --revision 8`. Artifact: `artifacts/polaris-boot-kali61-diag-v8.img`, SHA-256 `28d3687dcd0da420599751aeb07d2fe55f8e683c53fdbe5a1694ae7130ed4ad8`.

Revision 8 was booted with `fastboot boot` and reached the diagnostic shell over USB ACM. Live reads confirmed modem remoteproc `running`, `/run/wlfw-status` reporting `WLFW service 69 present`, and ath10k loading WCN3990 firmware API 5. `ip link set wlan0 up` succeeded; the interface reports `UP` with `NO-CARRIER` and a random locally administered MAC because the device-reported MAC was invalid. The initramfs does not include `iw`, `wpa_supplicant`, BlueZ, or D-Bus, so scanning, joining an access point, Bluetooth discovery, and pairing are not yet verified. Kernel logs registered the Synaptics S3330 input device and Bluetooth `hci0`; the QCA UART firmware setup completed. Touch coordinates remain untested. No phone partition has been written.

An earlier Alpine package staging attempt stopped because `apk update` reported `Quota exceeded`. Work then moved to the Ubuntu 26.04 arm64 base requested by the user. Ubuntu's official archive was verified, and the APT/wireless/BlueZ packages are now staged in `rootfs-ubuntu-26.04.1`; this is the initramfs root used by the new candidate.

The next diagnostic revision needs Wi-Fi and Bluetooth userspace before on-device scanning tests. The current phone is still running the v8 RAM image; it must be returned to Fastboot before another temporary boot.
